| BUG-01 | `AuthController.login` and `.me` returned 500 instead of 200 | Auth | High | `AuthControllerIntegrationTest` failing with `LazyInitializationException` | `User.role` is `FetchType.LAZY`; `AuthService.login()`/`.me()` were not `@Transactional`, and `spring.jpa.open-in-view=false` closes the Hibernate session before the mapper reads `user.getRole()` | Annotated both methods `@Transactional(readOnly = true)` | 3955ae6 |
| BUG-02 | `DepartmentRepository`/`CategoryRepository` failed application startup with `PropertyReferenceException: No property 'isActive' found for type 'Category'` | Department/Category | High | `DepartmentControllerIntegrationTest` failing to load the Spring context | Both entities store the flag as a field named `active` (JavaBean property `active`, getter `isActive()`); the derived query method was named `findByIsActiveTrue()`, which Spring Data parses as property `isActive` — a property that does not exist | Renamed both repository methods to `findByActiveTrue()`; corrected `database-schema.md` to match | (pending commit) |
| BUG-03 | `GET /api/categories` returned 500 instead of 200 | Category | High | `CategoryControllerIntegrationTest` failing with `LazyInitializationException` | `Category.department` is `FetchType.LAZY`; `CategoryService.getAll()`/`.getById()` were not `@Transactional`, and `spring.jpa.open-in-view=false` closes the Hibernate session before `CategoryMapper` reads `category.getDepartment().getName()` | Annotated both methods `@Transactional(readOnly = true)` | (pending commit) |
| BUG-04 | `POST /api/reports` with an image over `spring.servlet.multipart.max-file-size` (5 MB) returned 500 instead of the 413 documented in `api-standards.md` | Report | Medium | Written while implementing Phase 4 image upload; Spring's multipart resolver rejects oversized files before the request reaches the controller, throwing `MaxUploadSizeExceededException`, which `GlobalExceptionHandler` had no handler for (fell through to the generic `Exception` → 500 handler) | `GlobalExceptionHandler` had no `@ExceptionHandler(MaxUploadSizeExceededException.class)` case | Added a handler mapping `MaxUploadSizeExceededException` to `413 Payload Too Large` | (pending commit) |
| BUG-05 | `mvn spring-boot:run` failed application startup with `io.jsonwebtoken.security.WeakKeyException: ... 0 bits ...` | Auth/Config | High | Reported by user as a build failure | `jwt.secret=${JWT_SECRET:}` in `application.properties` intentionally defaults to empty (secret must come from a git-ignored local source), but no `backend/.env` or `application-local.properties` had been created yet on this machine, so `JwtUtil`'s constructor received an empty string and `Keys.hmacShaKeyFor` rejected the resulting 0-bit key | Created git-ignored `backend/.env` with a generated 256-bit `JWT_SECRET`, matching the mechanism `application.properties` already documents (`spring.config.import=optional:file:.env[.properties]`) | (not committed — `.env` is git-ignored) |
| BUG-06 | `DataSeeder` failed at startup with `org.postgresql.util.PSQLException: ERROR: prepared statement "S_1" already exists` | Config/Data | High | Surfaced immediately after fixing BUG-05, once the app could reach the DB | `SPRING_DATASOURCE_URL` points at Supabase's connection pooler on port 6543 (PgBouncer in transaction-pooling mode), which does not support server-side prepared statements; pgjdbc's statement cache tried to reuse a server-side prepared statement name (`S_1`) across pooled connections, which PgBouncer rejects | Appended `&prepareThreshold=0` to `SPRING_DATASOURCE_URL` to force pgjdbc to always use client-side (unnamed) statements | (not committed — `.env` is git-ignored) |
